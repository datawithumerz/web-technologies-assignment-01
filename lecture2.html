LECTURE 2

Web Applications and Architecture

A page of course information and a student results portal both run on the Web, but they have different needs. Application types describe how the experience works. Architecture describes how its responsibilities are organised.

  • Types of web applications

1. Why web standards matter

A web standard describes agreed ways for a technology to work. If browsers interpret the same HTML consistently, developers can write one page that works for many visitors. Without shared rules, pages may depend on features supported by only one browser.

The Web began with Tim Berners-Lee's work on sharing linked information. Early HTML focused on documents and hyperlinks. HTML later developed richer ways to describe content. XHTML applied stricter XML-style syntax, while the work that led to HTML5 placed strong emphasis on useful browser features and compatibility with existing pages.

HTML5 brought attention to semantic elements, native audio and video, and improved forms. These features let a page describe more of its meaning directly in HTML.

For a beginner, the practical lesson is to use meaningful elements, valid nesting and supported properties. A browser may recover from a mistake, but that does not make the original markup correct.

2. Static and dynamic applications

Static websites

A static website serves files prepared in advance. When a visitor requests a page, the server sends the existing file. A personal portfolio, course guide or small information website can work this way.

To change the written content, the developer edits the file and publishes the update. Static pages can still have useful navigation, styled links and HTML form controls.

<h2>Available courses</h2>
<ul>
    <li>Web Technologies</li>
    <li>Operating Systems</li>
</ul>
<a href="lecture3.html">Learn to write HTML</a>

This list is written directly into the HTML. It will not automatically update when a university changes its course database.

Dynamic applications

A dynamic application uses data or processing to produce or update content. A student portal may show different marks to different students. The system identifies the student, obtains the appropriate records and returns the result.

The difference concerns where the content comes from. A page does not become a dynamic database application simply because a link changes colour when you hover over it.

MPA, SPA and PWA

Different ways to deliver a web experience
TypeHow it worksExample
Multi-Page Application (MPA)Navigation loads separate documents or pages.Following a link from a home page to a lecture page.

These categories can overlap. Static or dynamic describes content delivery. MPA or SPA describes navigation. PWA describes additional capabilities. A site does not have to pass through these categories in a fixed order.

3. Layers and tiers

A layer groups a logical responsibility, such as displaying information or checking a rule. A tier describes a deployment separation: where a component runs. Several logical layers can run within one tier.

This distinction matters because splitting code into three files does not automatically create a three-tier system. The files might all run in the same environment.

One-tier architecture

The interface, processing and data are kept in one environment. A local inventory program that uses a local data file is a useful example. Setup is straightforward, but this arrangement is a poor fit for a large web system with many independent users.

Two-tier architecture

A client communicates directly with a server or data service. The client often handles the interface and some application rules. This can be suitable for a small system, but tightly combining rules and data access can make future changes harder.

Three-tier architecture

A common web design separates three responsibilities:

  1. Presentation: the interface that the visitor sees and uses.
  2. Application: processing, permissions and business rules.
  3. Data: stored records and their retrieval.

The browser communicates with the application, which accesses the data. This separation lets the application check what a user is allowed to do before reading or changing records. An N-tier system extends the idea with additional deployment tiers when needed.

4. Follow a request through a student portal

Imagine a student opening a page to view marks. The interface displays the request, but the application must decide which records that student can see.

Responsibilities in a three-tier portal
TierWhat happens
PresentationThe browser displays the student dashboard and a marks table.
ApplicationThe server checks the signed-in student and requests only that student's marks.
DataThe database stores users, courses and marks and returns the requested records.

Changing the colour of the marks table belongs to presentation. Checking whether a teacher can edit marks belongs to application logic. Saving the final marks belongs to the data responsibility.

A plain HTML table can demonstrate the interface, but it does not create authentication, enforce permissions or connect to a database by itself.

5. Choosing an architecture

More tiers create more work to deploy and maintain, so extra separation should solve a real problem. Consider the size of the system, how many people will use it, and how often it will change.

  • Scalability: can the system handle more users or data?
  • Maintainability: can one part change without forcing unnecessary changes elsewhere?
  • Cost: what equipment, hosting and maintenance effort does the design need?

A small guide with fixed lesson content can use static HTML files. A portal containing private student records needs additional application and data handling. Start with the responsibilities the system actually has.
